# Zivith 世界文件夹设计方案（V1）

> 状态：Proposal / 待实施\
> 目标：让 Zivith
> 的世界拥有一个稳定、可搬运、可恢复的本机文件身份，同时不破坏当前数据库驱动的运行架构。

------------------------------------------------------------------------

## 1. 目标

Zivith 的核心对象不是普通 Project，而是一个用户真正拥有的 **World / IP
世界**。

用户应该能够：

-   创建一个世界并选择本机文件夹；
-   关闭 Zivith 后再次打开该文件夹恢复世界；
-   移动整个文件夹后仍能识别为同一个世界；
-   不依赖固定绝对路径；
-   后续能够逐步支持 Git、版本控制、导入/导出；
-   不因为本次改造而重写当前已经闭环的数据库、Chat、Studio、Memory、Import、Roleplay、Production。

### 核心原则

> **V1：文件夹负责"拥有和搬运世界"，数据库继续负责"运行世界"。**

长期目标：

> **File System = Source of Truth**\
> **Database = Runtime Projection / Cache**

V1 不要求一次完成这个长期目标。

------------------------------------------------------------------------

# 2. V1 的边界

本阶段只解决：

1.  世界文件夹身份；
2.  `.zivith/workspace.json`；
3.  创建世界；
4.  打开世界；
5.  移动世界；
6.  重新绑定；
7.  基础异常处理；
8.  数据库与文件夹之间的 `worldId` 绑定。

暂时不做：

-   完整实体文件化；
-   数据库完全移除；
-   Git 自动集成；
-   文件级版本控制；
-   文件监听实时同步；
-   多人协作；
-   云端 Workspace；
-   `.ziv` 单文件压缩格式；
-   Organization；
-   新的实体类型。

------------------------------------------------------------------------

# 3. 推荐目录结构

V1 建议初始化为：

``` text
我的世界/
│
├── .zivith/
│   └── workspace.json
│
├── world/
│   ├── world.json
│   └── timeline.json
│
├── characters/
│
├── locations/
│
├── stories/
│
├── scenes/
│
├── sources/
│
└── assets/
    ├── images/
    ├── audio/
    └── video/
```

注意：

> V1
> 中这些目录主要承担"工程结构"和未来扩展作用，不要求所有内容立即写入文件。

数据库仍然保存当前完整运行数据。

------------------------------------------------------------------------

# 4. `.zivith/` 控制区

`.zivith/` 是 Zivith 世界工程的内部控制目录。

V1：

``` text
.zivith/
└── workspace.json
```

未来可以扩展：

``` text
.zivith/
├── workspace.json
├── version
├── cache/
├── indexes/
└── ...
```

其中：

-   `.zivith/` 是 Zivith 内部目录；
-   用户通常不需要手动修改；
-   Zivith 不应该把运行时缓存、日志、临时生成物随意写到世界根目录。

------------------------------------------------------------------------

# 5. workspace.json

建议结构：

``` json
{
  "format": "zivith-workspace",
  "formatVersion": 1,
  "worldId": "5364ad4e-108a-4cfd-98a0-01c4a833c92",
  "name": "龙族",
  "createdAt": "2026-09-12T10:00:00Z",
  "zivith": {
    "minVersion": "0.8.0"
  }
}
```

## 5.1 `worldId`

这是最重要的字段。

`worldId` 是世界的稳定身份。

必须满足：

-   创建后永久稳定；
-   不因为文件夹改名而改变；
-   不因为文件夹移动而改变；
-   不依赖绝对路径；
-   数据库中的 World/IP Core 使用同一个 ID。

例如：

``` text
D:\小说\龙族
```

移动到：

``` text
E:\IP\龙族
```

甚至改名：

``` text
E:\IP\我的东方世界
```

仍然：

``` text
worldId = 5364ad4e-...
```

------------------------------------------------------------------------

# 6. 世界与路径的关系

不要使用路径作为世界身份。

错误：

``` text
worldId = hash("D:/小说/龙族")
```

因为移动后身份会改变。

也不要让数据库保存：

``` text
worldPath = "D:/小说/龙族"
```

作为唯一身份。

正确模型：

``` text
World
├── worldId
└── currentPath
```

其中：

``` text
worldId = 永久身份
currentPath = 当前打开位置
```

路径只是定位信息。

------------------------------------------------------------------------

# 7. 创建世界流程

用户：

``` text
新建世界
```

然后：

``` text
输入世界名称
↓
选择文件夹
↓
检查文件夹
↓
创建 .zivith/
↓
生成 workspace.json
↓
生成基础目录
↓
创建数据库 World
↓
写入相同 worldId
↓
打开 Creator Chat
```

示例：

``` text
D:\Zivith Worlds\龙族\
```

初始化：

``` text
龙族/
├── .zivith/
│   └── workspace.json
├── world/
├── characters/
├── locations/
├── stories/
├── scenes/
├── sources/
└── assets/
```

------------------------------------------------------------------------

# 8. 打开世界流程

用户选择：

``` text
打开世界
```

选择文件夹。

Zivith 首先检查：

``` text
<folder>/.zivith/workspace.json
```

如果存在：

``` text
读取 workspace.json
↓
读取 worldId
↓
查询本地数据库
↓
找到对应 World
↓
更新 currentPath
↓
恢复 Runtime
↓
进入世界
```

这里不应该根据文件夹名称寻找世界。

例如：

``` text
文件夹名：龙族
```

只是显示名称。

真正身份来自：

``` text
workspace.json → worldId
```

------------------------------------------------------------------------

# 9. 搬家 / 重绑定

典型场景：

``` text
D:\Zivith Worlds\龙族
```

移动：

``` text
E:\Projects\龙族
```

然后打开。

Zivith：

``` text
读取 workspace.json
        ↓
发现 worldId
        ↓
数据库已有 worldId
        ↓
更新 currentPath
        ↓
恢复世界
```

不应该：

``` text
创建一个新世界
```

也不应该要求用户重新导入全部数据。

------------------------------------------------------------------------

# 10. 数据库的角色

V1 不删除数据库。

推荐：

``` text
                Zivith World
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
     File System             Database
     世界身份/工程              Runtime
          │                     │
          │                     ├─ Chat
          │                     ├─ Agent
          │                     ├─ Search
          │                     ├─ Timeline Query
          │                     ├─ Memory
          │                     ├─ Production
          │                     └─ Queue
          │
          └── workspace.json
```

数据库仍然是当前运行系统的主要数据源。

本阶段不要为了"文件化"而大规模迁移数据库。

------------------------------------------------------------------------

# 11. 长期架构方向

最终希望逐步演化为：

``` text
              Zivith World
                   │
                   ↓
          File System / .zivith
             Source of Truth
                   │
          ┌────────┴────────┐
          ↓                 ↓
       Runtime DB        Search Index
       Projection         / Cache
```

即：

> 文件保存世界本身，数据库负责让 Zivith 快速运行。

但这是长期目标，不属于 V1 必须完成的范围。

------------------------------------------------------------------------

# 12. 为什么不立即"一实体一文件"

虽然最终可以考虑：

``` text
characters/
├── character-a.json
├── character-b.json
└── ...
```

但 V1 不应该强制这么做。

原因：

1.  当前数据库模型已经可以运行；
2.  一次性迁移风险高；
3.  Agent 写入逻辑需要重新设计；
4.  文件同步与冲突处理复杂；
5.  Git Diff 设计尚未确定；
6.  文件结构现在还需要通过真实使用验证。

所以 V1 只建立：

``` text
世界文件夹
+
稳定 worldId
+
workspace.json
```

让后续文件化拥有稳定基础。

------------------------------------------------------------------------

# 13. world/ 目录

可以预留：

``` text
world/
├── world.json
└── timeline.json
```

## world.json

未来用于保存：

-   世界名称；
-   世界简介；
-   世界规则；
-   世界级设定；
-   世界元数据。

示例：

``` json
{
  "id": "world-001",
  "type": "world",
  "name": "龙族",
  "description": "现代世界与龙族共存的幻想世界",
  "rules": []
}
```

## timeline.json

未来用于保存世界时间线。

重点保留：

``` text
worldTime
presentationOrder
```

二者不能混为一谈。

例如：

``` json
{
  "id": "timeline-item-001",
  "type": "event",
  "entityId": "event-001",
  "worldTime": {
    "type": "absolute",
    "value": "2010"
  },
  "presentationOrder": 12
}
```

这样可以继续支持：

-   倒叙；
-   插叙；
-   平行时间线；
-   相对时间；
-   区间时间；
-   世界时间与呈现顺序分离。

------------------------------------------------------------------------

# 14. Character 文件的长期方向

未来可以：

``` text
characters/
├── 诺诺.json
├── 楚子航.json
└── ...
```

但是实体引用必须使用 ID：

``` json
{
  "characterId": "character-xxx"
}
```

而不是：

``` json
{
  "path": "./characters/诺诺.json"
}
```

原因：

用户可以：

``` text
诺诺.json
```

改成：

``` text
陈墨瞳.json
```

甚至移动目录。

实体 ID 仍然保持不变。

------------------------------------------------------------------------

# 15. Relationship 的设计

V1 不单独创建大量关系文件。

暂时保持数据库模型。

未来如果文件化，可以考虑：

``` text
world/
└── relationships/
    ├── relationship-001.json
    └── relationship-002.json
```

但不要提前做：

``` text
relationships/
├── 诺诺-楚子航.json
├── 诺诺-路明非.json
├── ...
```

因为关系本身可能随世界时间发生变化。

未来应该允许表达：

``` text
关系
+
时间
+
状态
+
修订
```

而不是把两个人的当前关系写死。

------------------------------------------------------------------------

# 16. sources/：原始资料

推荐保留原始资料：

``` text
sources/
├── 龙族Ⅴ.txt
├── 世界观资料.md
└── ...
```

原则：

> 原始资料与 AI 解析后的结构化世界分开。

流程：

``` text
原始资料
   ↓
AI 导入
   ↓
角色 / 地点 / 事件 / 关系
   ↓
Memory
   ↓
World
```

不要让 AI 解析结果覆盖原始资料。

这样以后可以重新解析、比较不同版本、重新进行知识提取。

------------------------------------------------------------------------

# 17. assets/

资源与知识继续分离：

``` text
assets/
├── images/
│   ├── characters/
│   ├── locations/
│   └── scenes/
├── audio/
└── video/
```

原则：

> Entity 描述"它是什么"，Asset 描述"它长什么样 / 听起来怎样 /
> 生成结果是什么"。

不要把所有东西重新抽象成一个巨大的 AssetRef 系统。

------------------------------------------------------------------------

# 18. 异常情况

## 18.1 文件夹没有 `.zivith/`

显示：

> 这不是一个 Zivith 世界。

提供：

``` text
[打开]
[导入为新世界]
[取消]
```

不要默认把普通文件夹直接当世界。

------------------------------------------------------------------------

## 18.2 workspace.json 损坏

显示：

> Zivith 世界配置文件无法读取。

提供：

``` text
[恢复]
[选择其他世界]
[取消]
```

不要静默覆盖。

------------------------------------------------------------------------

## 18.3 worldId 在数据库中不存在

说明：

``` text
这个世界文件存在，但当前本机没有对应的运行数据。
```

提供：

``` text
[重新绑定]
[创建运行副本]
[取消]
```

不要直接创建一个同名 World。

------------------------------------------------------------------------

## 18.4 worldId 冲突

如果发现数据库状态与文件状态不一致：

> 检测到世界身份冲突，请选择处理方式。

候选：

``` text
[使用文件世界]
[使用本地数据库]
[创建副本]
[取消]
```

V1 可以先只做明确错误提示，不做复杂自动合并。

------------------------------------------------------------------------

# 19. 路径管理

数据库可以保存：

``` text
worldId
currentPath
lastOpenedAt
```

但：

``` text
currentPath
```

只能作为本机最近位置记录。

不能作为世界身份。

如果路径不存在：

``` text
世界：龙族

上次位置：
D:\Zivith Worlds\龙族

当前文件夹不存在。

[重新定位]
[移除本机绑定]
```

重新定位后通过：

``` text
workspace.json → worldId
```

完成绑定。

------------------------------------------------------------------------

# 20. 安全原则

不要把以下内容写入世界文件：

-   API Key；
-   Provider Secret；
-   用户密码；
-   OAuth Token；
-   本机数据库密码；
-   其他敏感凭证。

尤其不能：

``` text
.zivith/workspace.json
```

里面出现：

``` json
{
  "apiKey": "sk-xxxx"
}
```

世界文件未来可能被：

-   Git 管理；
-   压缩分享；
-   上传；
-   发送给其他人。

凭证仍然由本机配置管理。

------------------------------------------------------------------------

# 21. Git 兼容性

V1 不实现 Git 功能，但目录结构应该天然兼容 Git。

未来用户可以：

``` text
git init
```

然后：

``` text
git add .
git commit
```

因此需要考虑 `.gitignore`。

例如未来：

``` text
.zivith/
```

不能简单全部忽略，因为 `workspace.json` 是世界身份的一部分。

更合理的是：

``` text
.zivith/
├── workspace.json       # 应进入版本控制
└── cache/               # 应忽略
```

所以未来：

``` text
.gitignore
```

可以忽略：

``` text
.zivith/cache/
```

以及临时文件。

# 26. 最终设计原则

### Principle 1 --- 世界身份不等于路径

``` text
World ID ≠ Folder Path
```

------------------------------------------------------------------------

### Principle 2 --- 文件夹可以搬家

``` text
Move
Rename
Copy
```

都不应该破坏世界身份。

------------------------------------------------------------------------

### Principle 3 --- V1 不拆数据库

先建立 Workspace，再逐步文件化。

------------------------------------------------------------------------

### Principle 4 --- ID 是引用的核心

文件名、目录名、显示名称都可以变化。

实体 ID 不应该因为这些变化而变化。

------------------------------------------------------------------------

### Principle 5 --- 原始资料不可被结构化结果替代

``` text
Source
    ↓
AI Understanding
    ↓
Structured World
```

三者保持可区分。

------------------------------------------------------------------------

### Principle 6 --- 文件不保存密钥

世界可以被复制、分享、版本控制。

凭证永远属于本机环境。

------------------------------------------------------------------------

### Principle 7 --- 不为未来过度设计

V1 的核心不是建立完美的 `.zivith` 文件格式。

而是验证：

> **"一个 Zivith 世界，真的可以属于一个文件夹，并且可以被用户带着走。"**

------------------------------------------------------------------------

# 27. 一句话结论

> **Zivith V1 世界文件夹 = 一个拥有稳定 `worldId` 的本机 IP
> 工程目录；`.zivith/workspace.json`
> 负责世界身份，数据库继续负责当前运行时，未来再逐步把世界实体迁移为真正的文件化
> Source of Truth。**
