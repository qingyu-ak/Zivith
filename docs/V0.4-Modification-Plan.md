## 0. 实现者必读（Guardrails）

任何 workstream 的实现都必须满足：

1. **不推翻现有设计**。线性 Story→Video 默认路径、审核门禁（visual-assets / prompt 强制门禁）、Project→Story→Scene→Shot 主干**不变**。
2. **迁移只做加法**。所有 Prisma migration 必须 additive（新表/新可空列/新枚举值）；禁止改写或重释已有行的语义（宪法 §8：兼容性债必须偿还，不得违约）。
3. **Headless 优先（P3）**。每个新能力先落 API/Orchestrator 操作，再落 UI；UI 不得拥有 API 没有的能力。
4. **Provider 概念不进 domain（P4）**。参考图注入等能力位定义在 ports/adapters 层；`packages/domain` 不出现任何供应商字段。
5. **溯源（P7）**。每次生成/重跑记录 provider、model、输入摘要；失败也记录。
6. UI 文案中文；代码注释与文档英文；每个 workstream 交付时同步更新对应文档（见各节 Doc sync）。
7. 每个 workstream 独立可合并：完成后 `pnpm lint / typecheck / test` 全绿，且线性 mock E2E 路径不回归。

## 2. W1 — 参考图注入生成管线（P0）

**目标**：图像生成从纯 text-to-image 升级为「锚定图 → 带标签参考 → 生成」，让角色/场景一致性有实现层，而不只有审核层。

### 改动

**Ports（`apps/api/src/ports/generation.ts`）**

- `ImageGenerationRequest` 增加可选 `reference_images?: Array<{ media_id: string; label: string; role: 'character' | 'location' | 'style' }>`。
- Adapter 能力声明增加 `supportsReferenceImages: boolean`（能力位，不是 provider 字段进 domain）。

**Adapters（`apps/api/src/adapters/siliconflow-image.ts`、`mock-generation.ts`）**

- SiliconFlow adapter：当模型支持 image-to-image / multi-image 输入时，把 reference images（转可访问 URL 或 base64）传入请求；不支持时**显式降级**并在 generation_metadata 记录 `reference_injection: 'skipped_unsupported'`。
- Mock adapter：把收到的参考图 label 写进 placeholder 元数据，便于测试断言。

**编排（`apps/api/src/contexts/visual/generate-requirement-image.ts`、`apps/api/src/contexts/workflow/mock-runner.ts`、shot 图/视频生成路径）**

- Visual Prep 出图：角色需求 → 取该角色已批准形象锚定图（W2；无则退回 `Asset.referenceImages[0]`）作为参考注入。
- Shot 视频生成（image-to-video）：沿用 Asset-Model §2.7 选择规则 — Scene approved binding 优先，其次 Asset 级 reference。
- prompt 合约（英文模板）：加入「reference labels are for identification only, never render them」「match art style of reference images」条款（吸收 waoowaoo prompt 工程结论）。

**Media 溯源**：`generation_metadata` 记录 `reference_media_ids[]`。

### 验收

- [x] 配了支持参考图的模型时，同一角色两个 Scene 的出图请求均携带同一锚定图（contract test 断言请求体）。
- [x] 模型不支持时不静默：metadata 有 skipped 记录，UI 徽标提示「本次未注入参考图」。
- [x] Mock 路径 E2E 不回归。

### Doc sync

- [x] Technical-Architecture.md（adapter 能力位 + `reference_images` 请求形状）
- [x] Asset-Model.md §2.7（选择规则不变，注明注入实现）
- [x] Next-Tasks.md F2、Implementation-Plan / V0.4 进度

## 3. W2 — 角色多形象 Appearance Variants（P0）

**目标**：一致性的单位从「角色」细化为「角色 × 形象状态」（如换装/受伤/年幼），每个形象有自己的描述与锚定图。深化 Asset，不加顶层概念（§3）。

### 改动

**Schema（`packages/database/prisma/schema.prisma`，additive）**

新表 `asset_appearance_variants`：

| 列 | 类型 | 说明 |
|----|------|------|
| id | uuid PK | |
| asset_id | FK → assets | 仅 character（首期）；location 后续再评估 |
| key | string | 稳定语义键，如 `default` / `wounded` / `young`；`@@unique([asset_id, key])` |
| title | string | 中文展示名 |
| change_reason | string? | 剧情变化原因（对齐评审 A1） |
| description | text? | 该形象的外观增量描述（与 Asset.appearance 合并解析） |
| anchor_media_id | string? | 已批准锚定图（Media） |
| candidate_media_ids | string[] | 候选图 |
| state | ApprovalState | draft/review/approved… 沿用现有枚举 |
| order / created_at / updated_at / deleted_at | | 常规 |

每个 character Asset 创建时自动带一个 `default` variant（migration backfill：为既有 character 生成 default variant，`anchor_media_id` 取 `referenceImages[0]`，无则空）。

**Domain（`packages/domain/src/schemas.ts` / `types.ts` / `resolution.ts`）**

- AppearanceVariant 类型 + 校验；解析规则：variant.description 覆盖/补充 Asset.appearance（与现有 base_character_id 继承同向：读时合并）。
- `VisualAssetRequirement.variant_key` 语义升级：优先匹配 `asset_appearance_variants.key`；无匹配时保持现状（自由字符串，兼容旧数据，不迁移旧行）。

**API（`apps/api/src/routes/resources.ts` 或新 route）**

- Variant CRUD + `POST /assets/:id/appearance-variants/:key/generate`（走 W1 管线，候选图落 `candidate_media_ids`）+ approve（选中候选 → `anchor_media_id`，state → approved）。此即 RFC Slice B「资产库独立出图」的资产侧入口。

**UI（`apps/web` 资产页）**

- 角色详情页：形象卡列表（形象名/变化原因/锚定图/候选图选择/生成按钮），中文文案。

### 验收

- [x] 既有角色数据零迁移损伤：老角色自动获得 default 形象且行为不变。
- [x] 可为角色建第二形象、生成并批准锚定图，全程无需 workflow run（Slice B 证据）。
- [x] Visual Prep 对 `variant_key` 命中形象时，注入该形象锚定图（W1 联动测试）

### Doc sync

- [x] Asset-Model.md §2.2（Appearance Variants — pending 标注已移除）
- [x] Domain-Model-Walkthrough.md（苏晚补 `appearance_variants` 例）
- [x] Next-Tasks.md F1 / E2、Implementation-Plan.md V0.4 进度

## 4. W3 — Story 有序分组 StorySegment（P1，ADR-0006）

**目标**：故事可按「章/幕」分段起草与审核；Scene 可归组；不分段的 Story 完全不受影响。

### 改动

**Schema（additive）**

新表 `story_segments`：`id, story_id FK, order, title, synopsis text?, draft text?, state ApprovalState, created_at/updated_at/deleted_at`，`@@index([storyId, order, deletedAt])`。
`scenes` 增加可空列 `segment_id`（FK → story_segments，`onDelete: SetNull` 语义 = 删除段落只解组不删 Scene）。

**Domain**

- StorySegment 类型/schema；不进入继承链（分组不是所有权，Scene 继承仍从 Story）。
- 排序一致性规则：segment 内 Scene 按全局 `scenes.order` 排序（单一事实源，避免双重排序漂移——ADR-0006 后果条款）。

**API**

- Segment CRUD + reorder（挂 Story 下，`/stories/:id/segments…`）。
- Scene 建/改支持 `segment_id`。

**Agent/Workflow（`packages/domain/src/workflow.ts`、`apps/api/src/contexts/workflow/mock-runner.ts`、agents）**

- Story Agent 输出升级为可分段：brief → `segments[{title, synopsis, draft}]`（LLM 结构化输出；mock responder 同步）。
- story review 门禁支持**逐段审核**：每段可单独 approve / retry_with_feedback；全部段 approved 后 story 步骤才完成（门禁类不变，属 gate 内政策，无需新 ADR）。
- Scene Agent 按段展开：为 approved 段生成 Scene 并写 `segment_id`。

**UI（`apps/web/components/workflow-panel.tsx` + story 页）**

- 故事审核卡片改为分段列表（每段：标题/正文/单独通过/按反馈重写），中文文案；无分段时退回现有单块展示。

### 验收

- [x] 旧 run / 旧 Story 完全不受影响（无 segment 时行为等同现状，回归测试）。
- [x] 新 run：故事按段生成，可只重写第 2 段而不动第 1 段的已批准内容。
- [x] 删除段落后其 Scene 仍在且 `segment_id = null`。
- [x] 禁止 UI 出现无持久化实体的假分段（ADR-0006 Compliance）。

### Doc sync

- [x] Core-Domain-Model.md §3/§4（已有 StorySegment 注）
- [x] Looser-Creative-Flow-RFC Slice C（Accepted 时已更新）
- [x] AI-Agent-Collaboration.md（Story Agent 输出契约改为 segments）
- [x] Next-Tasks.md F3 / E3、Implementation-Plan / V0.4 进度

## 5. W4 — 局部重跑 + 步骤 attempt 持久化（P1，RFC Slice A + 评审 A3）

**目标**：不 cancel+restart 就能重跑一个 Scene 的视觉准备 / 一个 Shot 的提示词或视频；每次执行留下可审计的 attempt 记录。

### 改动

**Schema（additive）**

新表 `workflow_step_attempts`：`id, workflow_step_id FK, attempt int, status, provider?, model?, input_hash, usage Json?, error_code?, error_message?, started_at, finished_at`，`@@unique([workflowStepId, attempt])`。
（`input_hash` = 步骤输入的稳定哈希，用于幂等判断与「输入未变可跳过」优化——吸收 waoowaoo GraphStepAttempt 经验。）

**Orchestrator / API**

- 新增 scoped recompute 操作（P3，先 API）：
  - `POST /scenes/:id/recompute-visual-prep`
  - `POST /shots/:id/recompute-prompt`、`POST /shots/:id/recompute-video`
- 语义：走 Orchestrator 生成 scoped 计划；下游**未批准**产物标记 stale（AI-Agent-Collaboration §4.1）；已批准产物不动；触达 visual-assets / prompt 门禁时照常停下（RFC 门禁硬规则）。
- 冲突规则：同一实体已有进行中的 scoped 重跑时拒绝并返回明确错误（RFC §14 冲突条款的最小实现）。

**UI**

- Scene / Shot 页与 WorkflowPanel 当前门禁处增加「重跑本场景视觉准备」「重跑本镜头提示词/视频」按钮（中文）。

### 验收

- [x] RFC Slice A 晋级证据：改一个 Scene 字段 → 局部重跑视觉 → 审核通过 → 继续，全程不 cancel+restart，含 stale 标记测试。
- [x] 每次（含失败）执行都有 attempt 行：provider/model/input_hash/usage。
- [x] 同输入重复重跑：input_hash 相同可被识别（日志或跳过策略）。

### Doc sync

Looser-Creative-Flow-RFC §14（补 API 形状与 stale 矩阵）、Next-Tasks E1 置 Done、AI-Agent-Collaboration §4。

## 6. W5 — 候选集标准化（P2，评审 A5）

**目标**：「一次生成 N 候选 → 人选一张 → 可回退」成为图像审核的标准交互。

### 改动

- 图像生成请求支持 `count`（1–4，默认 1）；候选统一落 `candidate_media_ids[]`（VisualAssetRequirement 与 W2 variant 已有此字段，语义对齐即可）。
- approve 动作 = 从候选中选中一张为 `approved_media_id` / `anchor_media_id`；**回退用 Media 历史与新一轮候选，不加 previousXxx 字段**（评审 C2 反面教训）。
- WorkflowPanel / 资产页：候选网格 + 选中态 + 重生成，中文文案。

### 验收

- [x] count>1 时一次任务产出多 Media 且全部可溯源（每张都有 generation_metadata）。
- [x] 审核门禁上可切换候选后 approve；已批准后再生成不覆盖历史 Media。

### Doc sync

Next-Tasks F5 Done、Technical-Architecture ImageGenerationRequest.count、README / Implementation-Plan near-term → W6。

## 8. W7 — 用量/成本记录 + 预算冻结（P3，后置，评审 A6 / C8）

**目标**：每次生成有价可溯（P7），为 agent 自主消费预设治理（§7 governance precedes autonomy）。首期只做**记录**，冻结/限额可二期。

### 改动（首期）

- 新表 `usage_records`：`id, project_id, task_type, provider, model, quantity, unit, estimated_cost?, metadata Json, created_at`；LLM/图/视/音每次调用（含失败）写一行。
- `GET /projects/:id/usage` 汇总接口 + 项目页简单汇总卡。
- 二期（另立任务）：预冻结-结算流水（参考 waoowaoo BalanceFreeze 形态）+ 批量重跑前成本确认（RFC 风险表 Economic 条款）。

### 验收
